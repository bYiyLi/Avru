# Avru 决定与开放问题

## 1. 已确认决定

本节只记录已有对话依据的决定。完整来源和验收见 [产品需求](requirements.md)，技术响应见 [技术设计](design.md)。

| 编号 | 决定 | 来源与影响 |
| --- | --- | --- |
| D-01 | 项目名称为 Avru，独立建立私有 GitHub 仓库。 | S-01、S-08。私有仓库不代表商标、npm 包名或域名已获保证；本次不发布软件。 |
| D-02 | 自定义浏览器扩展配合本机守护进程。 | S-01。运行对象是用户既有浏览器，不默认另开隔离的自动化浏览器。 |
| D-03 | 浏览器到守护进程是多对一。 | S-05。不能为每个浏览器各建一套独立控制守护进程。 |
| D-04 | AI 看见全部已连接浏览器的标签页，并自己选操作目标。 | S-06、S-07。用户无需逐次或逐页手动选目标；仍需内部准确路由与权限控制。 |
| D-05 | 对外通过 MCP 提供能力，使用 OAuth，并采用 FRPC 内网穿透链路。 | S-01、S-02、S-03。FRP 与 OAuth 承担不同责任。 |
| D-06 | 授权确认发生在目标电脑，不验证人是否在现场。 | S-04。远程桌面操作目标电脑允许，另一台电脑不能代替目标设备确认。 |
| D-07 | 用户不记、不复制、不填写 token。 | S-04。用户体验以同机确认为准；先前“简单 token 认证”不作为要求用户手动配置凭据的依据，也不取消协议和组件必要的内部身份凭据。 |
| D-08 | 用户自备 Node.js/npm，通过 npx 安装 Avru；支持 Windows/macOS，按用户登录后自启动设计。 | S-01、S-09、S-10。扩展引导由本地 Web 提供，安装仍遵循浏览器确认流程；无人登录运行未定。 |
| D-09 | CLI 以 `npx -y avru` 承担首次安装、自启动配置、启动和打开本地 Web；重跑检查更新、保留设置并确保启动和打开 Web；以 `npx -y avru uninstall` 独立卸载。 | S-10；对应 R-11、R-13、R-14。卸载停止守护进程、移除自启动与程序文件，配置数据由用户选择保留或删除。命令尚未发布验证，恢复与清理细节仍待 Q-06。 |
| D-10 | 浏览器选择、扩展安装引导、连接方式配置及运行状态归守护进程提供的本地管理 Web。 | S-10；对应 R-15。CLI 保持简单，不承担这些复杂交互、不静默安装扩展；不改变 AI 自行选择已连接目标的 D-04。 |
| D-11 | 扩展与守护进程采用本机 WebSocket；扩展使用 CDP / 浏览器扩展 API 控制网页。 | S-12；对应 R-17、design §5.3。多个浏览器直接连接单 daemon，不并行维护 Native Messaging，也不默认开放远程调试端口。身份配对和同机 OAuth 仍需 Q-03 完整设计与验证。 |
| D-12 | 受控浏览器 SDK 脚本采用 QuickJS WASM，由 daemon 管理单个独立、可复用的执行进程，不放入 daemon 主进程。 | S-11、S-13；对应 R-16、design §5.3.1、§6.1。运行器随 Avru 安装更新，用户无需单独安装或启动 QuickJS。守护进程逐次检查 SDK 调用权限；WASM 与进程复用不等于 OS 沙箱或跨任务隔离已验证。包/版本、宿主绑定、并发和资源限额仍待定。 |

这份清单不推断历史中未陈述的备选方案或理由，也不把助手提出的技术建议登记为用户批准的决定。

## 2. 开放问题

下列问题不阻止整理当前设计文档，但会阻止依赖它们的实现或对外承诺。解决后在对应需求/设计中更新正式合同，不将讨论结果只留在本清单。

| 编号 | 待决定问题 | 选项差异与影响 | 解决前不能宣称 |
| --- | --- | --- | --- |
| Q-01 | 公网入口、FRPS、域名及证书由谁部署和运营？ | 自托管与托管服务改变安装难度、费用、数据可见性、设备入口与租户边界；用户尚未选定。 | 用户无需任何公网配置即可用；云端绝不接触页面数据；具备多租户服务。 |
| Q-02 | “一个守护进程”按整台电脑还是按 OS 用户会话？ | 共享系统服务需要严格跨账号隔离和权限设计；每用户服务更贴合桌面会话但需明确与单机单进程要求的关系。 | 多用户电脑上的身份隔离与自启动方案已解决。 |
| Q-03 | 如何实现可验证的同机授权和扩展配对？ | 本机 WS 通道已由 D-11 确定，不再重选 Native Messaging；仍需冻结可信首次配对、双方身份验证、密钥保存/轮换/撤销及绑定 OAuth 请求的同机证明，不能仅判断 IP 或 localhost。 | 同机限制已安全实现；其他设备无法通过转发冒用；无额外浏览器限制。 |
| Q-04 | 一次授权如何覆盖新连接的浏览器？ | “设备范围动态覆盖全部已连接浏览器”更符合直观体验，但要明确未来连接纳入范围；“授权时快照”会有新的连接处理流程。两者都不能恢复每次人工选择标签页。 | 当前授权必然自动覆盖未来任何浏览器、配置或 OS 账号。 |
| Q-05 | 全部可见的权限边界是什么？ | 站点范围、隐身窗口、文件 URL、系统页面、密码字段和敏感操作需要明确规则；连接授权与业务动作许可分开。 | 安装扩展就能访问所有页面或执行所有网站操作。 |
| Q-06 | 已确认 CLI 生命周期之外，安装和发行如何实现？ | 目标命令、Node.js/npm 由用户提供、重跑更新、卸载选择及 CLI/Web 分工已由 D-08 至 D-10 确认。仍需核实 avru 包名可用性与发行主体，确定 Node.js/npm 及所需组件支持版本、FRPC 分发、安装路径、平台架构、签名/公证、更新策略与失败回滚、配置/凭据迁移、卸载清理范围和提权需求；版本不可用或数据未能清理等恢复语义尚未冻结。 | `npx -y avru` 或卸载命令已可执行；支持全部 Mac/Windows 版本；不需要任何系统权限；更新失败自动安全回滚。 |
| Q-07 | OAuth/MCP 具体协议合同与授权生命周期？ | 需固定 MCP/传输版本、客户端注册方式、授权端点部署、资源绑定、期限、刷新与撤销规则，并验证目标 ChatGPT 客户端。 | 已实现完整 MCP OAuth 兼容、永久授权或所有客户端兼容。 |
| Q-08 | 首版动作集和网页观察模型？ | 文本/结构/截图、点击/输入/导航、跨框架、JS、下载/上传等改变权限和实现；受控浏览器 SDK 与 QuickJS 已由 D-12 确定，但持续 JS 会话与任意执行不是既定需求。 | 列举过的全部操作都会进入第一版。 |
| Q-09 | 多客户端、多任务并发如何处理？ | 串行化、排队或冲突拒绝影响交互和执行安全；需明确超时、取消、重试与未知结果。 | 多 AI 可以无冲突同时控制同一页面。 |
| Q-10 | 具体浏览器、配置与平台版本矩阵？ | Chromium 系与 Firefox/Safari 的能力和分发不同；多浏览器是已确认目标，但“所有已连接”不等于承诺支持所有浏览器品牌。 | 已支持 Chrome、Edge、Firefox、Safari 的全部版本。 |
| Q-11 | 页面数据、诊断与审计的保存边界？ | 是否保存全文/截图、日志字段、保留周期、云端可见性和诊断上报影响隐私与运维；当前没有批准遥测或长期内容存储。 | 数据完全不留存、完全端到端保密或已具备审计合规。 |
| Q-12 | 是否需要脚本保存、重复运行、定时任务和工作流？ | 这会将实时浏览器控制扩展为自动化平台；Kivo 的相关设计不是 Avru 的默认范围。 | 已决定构建与 Kivo 相同的工作流平台。 |
| Q-13 | 性能、可靠性与容量目标？ | 需明确测试环境、浏览器/标签规模、延迟、恢复和资源占用口径，不能自行填写承诺数值。 | 已达到某个 SLA、吞吐或响应时限。 |
| Q-14 | QuickJS 与本机 WS 的具体实现合同？ | WASM 路线已由 D-12 确定；具体包/版本、宿主绑定、runner IPC、任务上下文与资源释放、异步/并发、WS 版本握手/消息限额/保活与重连、CDP 能力映射尚未冻结；按 design §5.3–5.3.1 的边界细化。 | 单进程已安全隔离任务、脚本能无限时运行或所有浏览器后台均可靠保活。 |

## 3. 建议的下一轮设计顺序

这不是获准执行的开发计划，也不设置负责人、日期或开发进度。

1. 先明确公网运营方式、OS 用户边界与浏览器支持矩阵。
2. 再选同机授权/配对机制，固定 MCP OAuth 合同，并审查从其他电脑、恶意网页及 FRP 入口发起的反例。
3. 确认最小动作集和数据权限，细化“发现 → 观察 → 操作 → 验证”的接口。
4. 在实现获得授权后，建立对应安装和运行验证方案；首先证明真实浏览器、守护进程与远程 MCP 的完整链路，不用 stub 代替集成验收。
5. 根据实际实现补充可用命令、开发计划和测试回执。未运行、失败、部分通过和完整通过分别报告。

## 4. 参考边界

本轮 WS/CDP 选择依据是多浏览器接入单 daemon 与减少 Native Host 注册的适配性，不是全行业使用率调查。Native Messaging 是有实际项目采用的备选，但未被 Avru 选为首版通道。

2026-11-07 已查源码的代表性参考（静态核查，未运行或安全测试）：

- [Tencent BrowserSkill 扩展 WS](https://github.com/Tencent/BrowserSkill/blob/7e862a44d19d0c1e492901fe29562cc7d79af590/apps/extension/src/transport/ws-transport.ts#L73)：扩展与 daemon 的 WS 路线；可参考多连接结构，不把其可选配对当作 Avru 默认安全合同。
- [OpenCLI 插件连接](https://github.com/jackwener/OpenCLI/blob/36bbbd7f60bd361a96e62e417a28ea09d6c2266b/extension/src/background.ts)：本机 WS、心跳与重连参考；不代表 Avru 已验证同等兼容性。
- [Kivo Native Messaging](https://github.com/bYiyLi/kivo/blob/9a0847de9cf207e95725a64767d201f5656b391a/extension/src/background.ts)：另一种实际桥接方式，用于比较跨平台注册和桥接进程的代价。
- [Browserable CDP 连接](https://github.com/browserable/browserable/blob/a3af19a66560d8bc3ff2c4ed4f9570eb6a66649c/tasks/services/browser.js)：Playwright 直接连接 CDP 的 WS，不是扩展到 daemon 的 WS，不能作为同类统计。

前述讨论还提到了 BrowserMCP 和 Playwright MCP 作为研究参考。参考项目的能力、许可证、版本和平台支持需要在实际采用时重新检查，当前没有作出代码复用决定。

已知 Kivo 的产品方向包含 AI 设计后由运行时重复执行；这一点只用于区分项目边界，不转成 Avru 已确认需求，也不把 Kivo 的测试结果当作 Avru 测试结果。

项目名称已由用户确定。此前 npm 页面 404 的观察不保证包名一定可发布；域名和商标仍未完成正式可用性确认。这些事项影响以后发行，不阻止本次私有设计仓库的创建。
