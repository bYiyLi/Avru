# Avru 产品需求

## 1. 目的与范围

Avru 让 AI 通过 MCP 控制用户正在使用的本机浏览器，减少用户在 AI 与浏览器之间手动选择、切换和操作的步骤。使用体验参考 Codex 的浏览器控制，不承诺复刻其内部实现或获得相同的平台权限。

本文面向项目所有者、开发者和验收人员，拥有产品要求及验收口径。技术设计见 [design.md](design.md)，决策与待定项见 [decisions.md](decisions.md)。

本版依据 2026-11-07 的项目定义对话整理。已确认要求与助手提出但尚未完成确认的功能建议分开记录。当前交付是设计文档，不是已实现产品，也不是冻结后的完整开发基线。

## 2. 参与者与系统环境

- **电脑使用者**：安装软件、安装扩展，在目标电脑上确认或管理连接。
- **AI 与 MCP 客户端**：例如 ChatGPT，通过 MCP 发现目标、读取页面、请求浏览器操作。
- **浏览器扩展**：连接到本机守护进程，在浏览器允许的范围内执行请求。
- **本机守护进程**：汇总浏览器连接，提供 MCP 与授权处理，路由请求和结果。
- **公网入口运营者**：负责 HTTPS 与 FRPS 的可用性、安全配置和可能接触的数据；由谁承担仍待决定。
- **网站与网站账号相关方**：浏览器操作可能读取其数据或改变其状态；Avru 的连接授权不替代网站规则或具体业务操作许可。

用户操作的是自己的既有浏览器会话。关闭、未安装扩展或未连接的浏览器，不属于“所有已连接浏览器”。同一电脑的不同操作系统账号如何隔离，仍未定案。

## 3. 已确认需求

下列验收是未来实现应达到的预期结果，尚未执行。R 编号用于后续设计与测试追踪，不代表优先级。

| 编号 | 单项要求 | 来源 | 可观察的验收 |
| --- | --- | --- | --- |
| R-01 | 项目使用 Avru 名称，作为独立浏览器控制项目维护。 | S-01、S-08 | 文档与发行标识一致；不以其他项目的实现或验收替代 Avru 证据。 |
| R-02 | 浏览器控制由自定义浏览器扩展与本机守护进程协作提供。 | S-01 | 经 MCP 发起的已授权操作由目标电脑上的扩展执行，并能定位执行目标与结果。 |
| R-03 | 同一目标电脑上的多个已连接浏览器共用一个守护进程。 | S-05 | 在最终支持矩阵内连接至少两个浏览器实例；同一个守护进程能分别识别和路由，断开一个不误操作另一个。 |
| R-04 | AI 可发现所有已连接浏览器的标签页，并自行选择目标，不要求用户先手动选择浏览器或标签页。 | S-06、S-07 | 给定已连接集合，发现结果覆盖全部可枚举目标；AI 能按明确目标标识操作其中一个，其他目标不受误操作。受限页面须明确标识，不伪装可控。 |
| R-05 | Avru 对外通过 MCP 向 ChatGPT 等客户端提供浏览器控制能力。 | S-01、S-02 | 在选定协议版本及目标客户端下完成连接、能力发现、调用与结果返回；不以自定义非 MCP 接口代替验收。 |
| R-06 | 对外 MCP 连接使用 OAuth 授权。 | S-03、S-04 | 未授权或失效凭据不能调用受保护能力；目标客户端完成符合选定 MCP 授权规范的连接流程。 |
| R-07 | 远程连接链路使用 FRPC 内网穿透，将公网入口连接到目标电脑上的服务。 | S-01 | 目标网络条件下，MCP 请求经已配置的 FRPC/FRPS 链路抵达正确设备；隧道故障能被识别为不可用。 |
| R-08 | OAuth 授权的用户确认必须在目标守护进程所在的同一台电脑上完成。 | S-04 | 仅在另一台电脑打开授权链接无法完成目标电脑授权；另一台安装了 Avru 的电脑也不能冒充目标电脑确认。 |
| R-09 | 在目标电脑上通过远程桌面完成的授权确认属于允许的使用方式。 | S-04 | 在受控测试中，通过远程桌面操作目标电脑可完成与本地操作相同的确认；不增加“人必须在现场”的判定。 |
| R-10 | 安装和授权不要求用户记、复制或手动填写 token。 | S-04 | 正常安装、扩展连接及 MCP 授权流程没有用户手抄 token 步骤；系统必要凭据不回显给 AI 或暴露在页面内容中。 |
| R-11 | 使用 npx 作为安装入口，并在安装流程中引导用户安装浏览器扩展。 | S-01 | 在最终支持的环境中，npx 入口完成守护进程安装并给出有效扩展引导；用户取消、安装失败或扩展未连接时如实显示未完成。 |
| R-12 | 支持 Windows 与 macOS，并在用户登录后自动启动本机服务。 | S-01、S-09 | 两个平台在最终版本矩阵中完成首次安装、退出安装终端、重新登录后的自启动测试；浏览器关闭时显示离线，不声称可控制页面。 |

**R-04 的范围说明**：已确认的是全部已连接浏览器可用、不逐个要求用户选定操作目标。现有授权是否自动覆盖以后新增的浏览器连接，属于授权生命周期问题，见 Q-04；不能借此恢复“每次操作先让用户选浏览器”的交互。

**R-08 的判定说明**：“同机”指确认经目标电脑的受信本机组件完成。公网请求经过隧道、来自相同公网 IP 或携带设备名称，都不能单独证明同机。具体证明机制见技术设计候选及 Q-03。

**R-10 的判定说明**：取消的是用户管理 token 的交互要求。OAuth 和组件之间仍需要系统自动管理的身份凭据，不能解释为公网接口无需认证。

## 4. 已提出、尚未冻结的功能范围

此前方案提出以下基础操作，适合用于后续最小闭环设计，但尚没有逐项确认完整语义、权限或支持矩阵：

- 读取页面结构或文本、截图。
- 点击、输入及标签页操作。
- 查看连接状态、停止当前控制、撤销授权。

以下内容也尚未定案：滚动、导航、表单提交、快捷键、跨框架操作、下载、上传、任意 JavaScript、持续 JS 会话，以及脚本保存和重复执行。它们不能因“参考某项目”而自动进入首版承诺。

产品默认可见全部已连接标签页，与网站访问权限、隐身窗口权限、敏感操作许可是不同层次。浏览器不允许扩展访问的页面不能绕过；具体授权粒度待 Q-05 决定。

## 5. 约束、依赖与非目标

- 扩展安装需要遵守浏览器支持的安装与用户确认流程；npx 是引导入口，不承诺静默安装。
- npx 入口不等于常驻进程本身。需要独立的持久安装位置、自启动注册和生命周期管理设计。
- 当前“自启动”按用户登录后的桌面会话解释，不承诺无人登录时控制用户浏览器。
- 用户退出、电脑休眠、浏览器关闭、扩展离线或网络中断会影响可用性，恢复语义必须说明。
- FRP 提供连接，不替代 OAuth、本机组件认证或页面操作权限检查。
- 没有批准默认开放调试端口、任意文件系统访问或通用 shell 执行。
- Avru 的连接许可不能自动授权付款、删除数据、发送消息等具体网站操作。
- 当前不包含 Giunto 的 SDK 扩展平台，也未决定继承 Kivo 的脚本与工作流能力。
- 本版不确定编程语言、运行时版本、MCP SDK、数据库、扩展框架、云端租户体系、商业模式或发布许可。
- 性能、容量、可用性指标与最低操作系统/浏览器版本没有已批准数值；不能填写任意目标并称为承诺。
